# 추천 미리보기 대기 복구와 회귀 검증

사용자 승인: “그래 해 봐”. 직전 제안한 추천 → 수정 → 선택 안정성 점검 및 기존 native 충돌 조사를 진행했다. 기준은 dev `ab19967681a7455b62f9b50b8825f8f16cf1f3d2`, 복귀 태그는 `dev-before-preview-stability-2026-09-19`다.

## 변경

- `RecommendationPreviews.cs`: 요청별 120초 대기 제한. 응답이 유실된 후보는 오류로 표시하고 다음 후보를 처리한다. 다음 후보 선택과 수정은 계속 가능하다.
- 요청 객체의 동일성을 확인해 늦게 완료된 옛 요청이 새 후보의 대기 상태나 이미지를 바꾸지 못하게 했다. 늦은 요청도 원래 설정으로 그리도록 약한 참조 스냅샷 매핑은 완료 콜백 또는 GC까지 보관한다.
- 제품은 Map Preview 공유 큐를 비우거나 worker를 중단하지 않는다. 실제 생성이 느려 제한을 넘겨도 같은 안내가 나올 수 있다. 큐 전체가 멈춘 경우 다음 요청도 각각 제한 시간 이후 오류가 되며, 외부 worker 자체를 복구하는 기능은 아니다.
- 생성 엔진·추천 내용·모델 설정·저장 형식은 변경하지 않았다. 이미지 입력/해석은 계속 꺼져 있다. Fable/Claude 및 새 공급자 호출은 0회다.

## 검증 방법

`tools/runtime-probe/launch.ps1 -Render -CandidatePreviews <기존 응답 폴더> -CandidateStressRounds 6`으로 실제 게임에서 저장 응답을 재생한다. 한국어에는 `-CandidateQueueLoss`를 추가했다. 사용자 프로필이나 저장 파일은 사용하지 않는다.

queue-loss 시험은 별도 시험 게임의 worker를 잠시 대기시킨 뒤 다음 후보 요청 하나를 큐에서 제거한다. 기존 Map Preview의 `ClearQueue()`는 제거한 요청의 promise를 종료하지 않는다. 125초 뒤 화면 상태를 비교하고, 수정본에서는 다른 두 후보 완료 → 첫 후보 수정 → 유실됐던 옛 요청 재전송 → 새 후보 선택 → Undo까지 검사한다. 공유 큐 조작은 이 격리된 시험에만 있다.

- `dotnet run --project dev/Source/Tests/TextToMap.Tests.csproj --no-restore`: 기존 회귀 150 PASS / 0 FAIL. [전체 출력](tests.log).
- 제품 `dotnet build dev/Source/MapGenAI.csproj --no-restore --nologo`: 오류 0, 기존 버전 문자열 경고 1. [출력](build-r1.log). 최종 DLL SHA256 `4010d0decee7a5d485c944bbf1877421a48020a7800693e837cbd02de23018ef`.
- 기준 DLL에서 한영 각 6회 수정 반복. 수정 DLL에서도 같은 응답·상태로 반복한다. 다른 후보 보존, 자연스러운 통로와 정확한 통로 전환, 선택 후 일반 미리보기와 픽셀 일치, 단일 Undo, 취소·오류·닫기·seed/크기 변경을 검사한다. [독립 평가](../../../tools/evaluate_preview_stability.py)의 `evaluation.json`을 최종 수치의 근거로 사용한다.
- 최종 결과: 기준 한영 352검사, 수정본 한영 361검사 PASS. 원래 후보 18그림의 픽셀 해시가 동일하고, 수정/선택 후 일반 미리보기와 비교한 30개도 62,500픽셀씩 일치했다. 기존 DLL의 큐 유실은 79번째 검사에서 예상대로 실패했으며 수정본의 동일 검사는 통과했다. [평가 결과](evaluation.json). 성공한 네 실행은 수정 반복을 각각 6회 수행했다.
- 새 완성맵 생성 검사는 수행하지 않았다. 이번 UI 대기 변경의 검증은 기존 회귀와 실제 미리보기·상태 전환이다. 저장 응답 재생이므로 모든 새 자연어 응답이나 외부 모드 조합의 보장은 아니다.

## 보존한 실패와 한계

1. 원래 MG23의 [native 충돌](../2026-09-19-candidate-refinement/native-final-ko/Player.log)은 **원인 미확정·미해결**이다. 로컬 minidump에서 Mono 모듈 `+0x4fc3e3`의 write access violation을 확인했다. [예외 메타데이터](prior-crash-summary.json)만 내보냈으며 원시 메모리 dump는 게시하지 않는다. 가까운 export 심볼만으로 실제 오류 함수를 단정하지 않는다. 반복 실행에서 재현되지 않았다는 사실은 해결 증거가 아니다. 이번 timeout 수정과 해당 충돌의 인과관계도 확인되지 않았다.
2. 새 시험 도구의 초기 `queue-baseline`, `recovered-ko`, `recovered-en`은 후보 검사 시작 전 선택 어셈블리 로딩 문제로 중단됐다. 정적 람다가 만든 `Func<MapPreviewResult,bool>` 캐시 필드가 원인 후보였고, [IL 근거](harness-optional-field-failure.txt)를 보존했다. 명시적 delegate 생성으로 고친 동일 시험 도구에서 검사가 정상 시작됐다. 초기 3개는 성공 수치에 합산하지 않는다. 각 폴더에 소유 프로세스 중단·정리 영수증이 있다.
3. 기존 DLL의 `queue-baseline-r2`는 의도적으로 유실시킨 요청에서 대기가 끝나지 않는 실패를 보존한다. 수정본이 같은 검사와 늦은 응답 보호를 통과하는지 독립 평가한다.

## 사용자가 확인할 흐름

1. `추천해 줘` → 그림 세 개 표시.
2. `3번 통로를 자연스럽게 해 줘` → 3번만 새 그림, 나머지 두 그림 보존.
3. `3번 통로 다시 반듯하게 해 줘` → 원래 윤곽으로 복원.
4. `3번` → 해당 결과 적용, 되돌리기 한 번으로 추천 전 상태 복원.

일반 사용에서 120초를 일부러 기다릴 필요는 없다. 요청 유실 복구는 위 격리 시험으로 검사한다. 이전 강제 종료가 다시 발생하면 그 실행의 로그와 마지막 동작을 기준으로 추가 조사해야 한다.
