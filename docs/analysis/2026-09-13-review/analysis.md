# MapGenAI 개선 분석 — 보존판 v1.6에서 dev로

2026-09-13 · Codex 자체 분석 + Claude Fable 독립 검토 · 기준 `1439bbdfac7601f6c668be49681f7d8f6073af09`

**현재 엔진을 살릴 가치가 있다. 다만 모델을 교체하기 전에 ‘실제 변경 여부’와 ‘기존 특징 보존’을 검증할 수 있게 만들어야 한다.** 이후 복잡한 자연어는 위치 관계를 명시하는 편집 명령으로, 이미지 입력은 인식 결과를 확인·수정할 수 있는 영역 편집으로 발전시키는 방향을 권한다. 예전에 포기한 **이미지·그림→맵과 복잡한 자연어 지형 생성 둘 다** 이번 검토에 포함했다.

`v1.6` 태그와 `dev` 브랜치는 같은 기준 commit으로 GitHub에 보존했다. 이번 분석에서는 게임 코드를 수정하거나 새 버전을 배포하지 않았다. 아래 우선순위는 제안이며, 과거 사용자 결정과 새 구현 승인을 혼동하지 않는다.

## 1. 현재 모드에서 살릴 것과 부족한 것

모드의 중심은 **자연어 → JSON 편집 지시 → 타일별 상태 병합 → 생성 패치·미리보기**다. 밀도·동굴·석재·강·해안·타일 특징과 고도 도형을 다루며, 프리셋과 Undo도 이미 있다. 특히 일부 키만 바꾸고 나머지를 유지하는 구조는 사용자의 “기존의 특징들을 유지하면서”라는 요구에 맞는다. 9월 수정에서 특징 추가를 합집합으로 바꾼 것도 이 방향이다. [현재 상태 병합 코드](https://github.com/rucy74/MapGenAI/blob/1439bbdfac7601f6c668be49681f7d8f6073af09/dev/Source/MapGen/MapGenParams.cs#L326)

복잡한 형상을 전혀 표현할 수 없는 엔진도 아니다. SDF 합성에 원·타원·다각형·별 등의 프리미티브, 정규화 좌표, 회전과 합성 연산이 있다. 부족한 부분은 “섬을 호수 안에”, “기존 북쪽 산을 남쪽으로 옮겨” 같은 **대상 식별과 관계를 안정적으로 해석·검증하는 단계**다. 현재 폐허 밀도 조절은 특정 섬 위에 건축물을 배치하는 기능과 다르며, 확인한 fill 목록에 용암은 없다. [도형·채움 구현](https://github.com/rucy74/MapGenAI/blob/1439bbdfac7601f6c668be49681f7d8f6073af09/dev/Source/MapGen/SdfComposite.cs)

현재 LLM은 상태 요약을 읽지만 실제 생성된 맵은 보지 않는다. UI의 설명도 적용 전후 결과로 작성되지 않는다. 따라서 ‘JSON을 받음’, ‘설정이 바뀜’, ‘미리보기가 갱신됨’, ‘요청한 지형이 만들어짐’을 지금보다 명확히 구별해야 한다. [응답 처리](https://github.com/rucy74/MapGenAI/blob/1439bbdfac7601f6c668be49681f7d8f6073af09/dev/Source/UI/Dialog_TextToMap.cs#L782)

## 2. 지금 확인한 결함

증거 수준을 구별했다. **재현**은 이번에 실행한 결과, **정적 확인**은 현재 소스에서 확인한 경로이며 게임 증상까지 재현했다는 뜻은 아니다. 상세 입력·소스 위치·실행법은 [검증 근거](evidence.md)에 있다.

| 우선 | 문제 | 확인한 증거와 사용자 영향 |
|---|---|---|
| P0 | 잘못된 JSON에서 파서가 끝나지 않음 | 변형하지 않은 `SimpleJson.cs`에 잘못 닫힌 배열을 전달하자 2초 제한까지 반환하지 않아 프로세스를 종료했다. 문자 위치가 전진하지 않는 반복 경로가 있다. 게임 UI 스레드에서 호출되므로 멈춤 위험이 있다. 실제 서비스 응답의 발생 빈도는 미측정. |
| P1 | 빈 편집과 전체 복원이 구별되지 않음 | `explicitKeys.Count == 0`이 전체 적용을 뜻한다. 빈 params나 지원하지 않는 키만 받은 경우에도 기존 상태가 기본값으로 교체될 수 있다. `elevation_shapes:[]`는 객체 배열로 읽히지 않는 현상도 재현했다. |
| P1 | 복합 도형의 저장·복원 누락 | `ToSnapshot`, `ExposeData`, 프리셋 직렬화 모두 composite 내부 도형·연산을 빠뜨린다. Undo·세이브·프리셋 경계를 통과하면 정보를 보존할 수 없는 코드다. 실제 로드 후 렌더링 증상은 미검증. |
| P1 | 제거한 특징을 다시 추가할 때 충돌 | 예전 `removeMutators`가 남고 적용 마지막에 재차 제거된다. 다음 대화에서 같은 특징을 추가해도 사라질 수 있는 정적 경로다. |
| P1 | 편집 의도가 서로 섞임 | 강 X만 보내도 Z를 기본값으로 덮어쓴다. 자동 산은 누적되므로 ‘추가’에는 맞지만 ‘이동/삭제’와 구분이 부족하다. 전송 시 Undo를 쌓아 되물음·실패에도 중복 이력이 생긴다. |
| P1 | 성공 표시가 실제 결과와 분리됨 | 알 수 없는 action에는 명시적 실패 처리가 없고, 응답 설명과 실제 상태 차이를 대조하지 않는다. Steam의 ‘안 바뀜’ 제보와 관련된 조사 지점이지만 그 제보의 원인으로 확정하지 않았다. |
| P1 | 기존 자동 테스트를 실행할 수 없음 | 기준 소스 빌드는 성공했으나 Tests 프로젝트는 타입 참조 누락으로 오류 5개. 반복 편집 회귀를 막을 기반이 작동하지 않는다. |

추가로 유니코드 이스케이프 오해석과 닫히지 않은 JSON의 수용을 재현했다. `Apply(data, tileId)`와 mutator 처리의 선택 타일 재조회 불일치, 공유 GenStepDef 임시 수정의 예외 복원도 후속 검증 대상이다. 지금은 실제 타일 오적용이나 게임 크래시가 재현됐다고 주장하지 않는다.

## 4. 예전에 포기한 작업은 왜 막혔나

`experiment/image-to-heightmap @8c244555`를 체크아웃·병합하지 않고 복원했다. 이미지 생성 마스크, K-means 분할, LLM 문자 격자, native segmentation v2 설계로 접근이 바뀌었다. 토큰 증가·온도 조정·격자 축소·행 보정이 반복됐고, 부족한 셀을 기존 문자로 반복 채우는 경로도 있었다. 이것은 형식을 통과시켜도 원본 지형과의 일치를 검증하지 못한다. [과거 검토 원문 사본](evidence/history/2026-06-03-macro-review-4axis.md)

6월 보고에 기록된 **과거** Gemini 2.5 Flash 실험은 18회다. thinking on 쪽은 엄격 파싱 0/9·평균 55.9초, thinking off 쪽은 8/9·6.4초였지만 단일 문자나 반복 행으로 퇴화한 출력이 나왔다. 이번에는 해당 API 실험을 재실행하지 않았다. 두 조건은 thinking과 출력 예산을 함께 바꿨으므로 속도 차이 전부를 thinking 하나의 인과 효과로 해석할 수도 없다.

따라서 기록이 보여주는 것은 “당시 Opus가 못했으니 지금 Fable이면 된다”가 아니다. 개발에 사용한 모델과 모드가 호출하는 모델, 출력 계약, 상태 적용, 품질 평가가 모두 다른 변수다. 복잡한 자연어에서도 좌표 JSON만 맞는지 검사하면 ‘호수 안의 섬’이 실제로 성립하는지 알 수 없다.

당시 승인된 방향은 유지해야 한다. **원본 재현 우선, 불가능하면 합리적 해석, 영역 클릭과 채팅 수정, 지원하지 않는 요소의 대체 설명**이었다. top-down 입력은 분할 방식, 사선 사진은 의미 해석 후 top-down 후보 두 개 비교를 구상했다. 이후 진행을 보류했고, 흑백 높이맵만 남기자는 후속 분석 의견은 사용자 결정이 아니었다. [4월 승인 사양](evidence/history/2026-04-12-1900-spec-image_to_map_v2.md), [당시 대화 기록](evidence/history/2026-04-12-session.md)

현재도 재사용할 자산은 있다. 실험 브랜치의 `GridBuilder`는 지형 레이블을 고도·비옥도 격자로 바꾸며 palette와 미리보기 관련 기반이 있다. 이 부분을 추출해 검증할 수 있다. 오래된 브랜치 전체를 dev에 병합해 최신 신뢰성 수정을 다시 잃는 방식은 피한다.

## 5. 권장 개발 항목

순서는 의존 관계를 고려한 제안이다. 규모는 상대적이며 작업 기간 추정이 아니다. P0/P1은 기존 약속의 신뢰성을 확보하고, P2에서 두 보류 기능을 단계적으로 확장한다.

| ID·우선·규모 | 사용자에게 달라지는 점 | 구현 방향 | 합격 조건 |
|---|---|---|---|
| I01 · P0 · 중 | 이상한 응답 때문에 UI가 멈추지 않음 | 엄격한 파싱·크기/깊이 제한·오류 격리. net472 및 다른 모드와의 호환을 확인해 성숙한 JSON 파서 도입 비교 | 잘린 응답·잘못 닫힌 배열·과도한 중첩을 제한 내 거부, 상태와 Undo 불변 |
| I02 · P1 · 중 | 빈 응답이 맵을 초기화하지 않음 | `Patch`와 `RestoreSnapshot`을 명시 분리. 키 없음/null/빈 배열의 계약 확정 | 빈·미지원 patch는 변경 없음, 도형 빈 배열 clear는 의도대로, 부분 변경은 다른 값 유지 |
| I03 · P1 · 중 | 제거·재추가·이동·Undo가 예상대로 됨 | 추가/제거 충돌 해소, 성공한 변경에만 이력 추가, 강 X/Z 독립, 산 대상 식별 | 고정된 20턴 편집에서 요청 밖 상태 보존, 추가→제거→재추가와 되물음→Undo 통과 |
| I04 · P1 · 중 | 만든 복합 지형을 다시 불러와도 유지 | 도형·연산·중첩 배열까지 저장/깊은 복사, 버전 있는 공통 상태 계약 | snapshot·preset·게임 저장/로드 전후 도형과 연산 동일, 독립 사본 수정이 원본에 영향 없음 |
| I05 · P1 · 중 | 무엇이 바뀌고 거절됐는지 보임 | 실제 상태 diff, no-op·거부 이유, 미리보기 완료 상태 표시 | LLM 설명이 성공이어도 diff가 없으면 변경 완료로 표시하지 않음. 미리보기 오류를 분리 보고 |
| I06 · P1 · 중 | 같은 문제를 재현하고 회귀를 막음 | 실행 가능한 상태 병합 테스트와 고정 seed 평가. 응답·버전·전후 상태·미리보기 기록 | 기준 사례 재실행 가능, 실패 위치를 해석/병합/적용/생성으로 구분. 키 등 비밀 제외 |
| I07 · P1 · 소~중 | 설정과 공급자 오류가 이해됨 | 연결·모델·응답 형식 확인, 제한/타임아웃/중단 이유 구분, 공급자별 구조화 응답 어댑터 | 각 지원 공급자의 정상·인증 실패·빈 응답·잘림 경로 구별. 모델 공통 온도값을 무조건 강제하지 않음 |
| I08 · P2 · 중~대 | 복합 요청을 공간 관계대로 만듦 | 대상 ID, 영역, `inside/near/avoid/preserve` 등 관계와 add/move/remove 명령을 계획으로 정리 후 기존 SDF로 실행 | 중앙 섬·주변 물·보존 영역을 수치로 검사. 해석이 맞지만 엔진 미지원인 요청은 별도로 설명 |
| I09 · P2 · 중 | 실패한 지형을 제한된 횟수 안에 교정 | 실제 고도/지형/연결성 지표를 확인하고 위반 부분만 재계획. 필요할 때 미리보기 이미지 참고 | 동일 seed에서 제약 위반 감소, 보존 영역 불변, 횟수·시간 예산 초과 시 이전 유효 결과 유지 |
| I10 · P2 · 중 | 지도·스케치를 원본에 가깝게 변환 | 색상/레이블 입력 → 결정적 격자 변환을 먼저 복구. AI는 의미 라벨과 애매한 영역에 사용 | 정답 있는 지도에서 영역·방향 일치, 축/회전 오류 없음, 부족 셀을 반복 채워 성공 처리하지 않음 |
| I11 · P2 · 대 | 사진·그림을 해석하고 직접 교정 | 모델별 분할 계약 probe, 영역 클릭·채팅·palette 수정. 사선 이미지는 top-down 후보 비교 | 원본에서 확인 가능한 특징 보존, 추정·대체 요소 표시, 선택 영역만 교정. 단일 지형 입력도 정상 처리 |
| I12 · P2 · 소~중 | 처음부터 가능한 요청을 알 수 있음 | 지원 기능 예제·현재 타일 제약·평가 근거가 있는 모델 안내·좋은 결과 프리셋 | 예제 모두 지정 버전에서 재실행. 미지원 용암/구조물 배치를 지원한다고 안내하지 않음 |

‘섬 위 유적’까지 완전히 지원하려면 별도의 구조물 배치 기능이 필요하다. 우선 섬과 호수의 관계를 통과시킨 뒤 건물 footprint·충돌·이동 가능성·바이옴/모드 의존을 확인하는 후속 과제로 두는 것이 타당하다. 기존 `ruin_density`에 좌표를 억지로 붙여 해결됐다고 간주하지 않는다.

I03의 제거 기록은 단순히 매번 비우면 안 된다. 현재 코드는 원래 타일 특징을 복원한 뒤 다시 적용하므로, 삭제 상태를 잊으면 원래 특징이 다음 턴에 부활할 수 있다. 유지할 최종 상태를 일관되게 관리하거나, 재추가한 항목만 제거 기록에서 빼는 식으로 계약을 먼저 정해야 한다. Undo 역시 변경 **전** 스냅샷을 확보하고 성공이 확인된 뒤 이력에 확정해야 한다.

## 6. 두 보류 기능을 다시 시도하는 구체적 방법

**복잡한 자연어:** ‘용암 호수 가운데 섬과 유적’을 받으면 호수 영역, 그 안의 섬, 섬 위의 구조물이라는 계획으로 나눈다. 지원하지 않는 재질·구조물은 실행 전에 표시한다. 지원되는 부분은 기존 SDF로 만들고, 섬의 연결된 육지 여부·물에 둘러싸인 비율·중심 위치를 실제 격자에서 검사한다. 다음 요청은 전체 맵 재생성보다 특정 대상을 편집하게 한다. 단순 수치 변경에는 이런 다단계 처리를 강제할 필요가 없다.

**이미지·그림:** 입력을 보고 있는 그대로의 지도를 옮길 수 있는지, 사선 사진의 보이지 않는 부분을 해석해야 하는지 구별한다. 지도·스케치는 결정적 색상/레이블 변환을 기준선으로 삼고, 사진은 분할·해석 결과를 중간 미니맵으로 보여준다. 사용자는 영역을 선택해 ‘여기는 물이 아니라 산’이라고 고친다. 흑백 높이맵은 빠른 입력 선택지로는 유용하지만 기존 승인 범위를 대체하지 않는다. 두 경로 모두 최종적으로 검증된 레이블/고도 격자에 연결한다.

모델별 이미지 응답 형식은 다시 확인해야 한다. 현재 공식 문서는 Gemini 3 Pro/3 Flash의 픽셀 마스크 제약을 설명하는 한편, 별도 이미지 문서는 3.8 Flash의 다각형 좌표 분할 예제를 제공한다. 모델 세대와 API 계약이 다르므로 옛 마스크 디코더에 모델명만 바꾸는 접근은 적절하지 않다. **실제 모델 한 종의 작은 응답·품질 probe를 먼저 통과시켜야 한다.** [Gemini 3 가이드](https://ai.google.dev/gemini-api/docs/gemini-3), [이미지 분할 문서](https://ai.google.dev/gemini-api/docs/image-understanding#segmentation)

## 7. 평가를 먼저 작게 설계한다

- **상태 편집:** 추가→제거→재추가, 왼쪽 산 보존하며 오른쪽 산 추가, 산 이동, 강 X/Z 순차 수정, ask/실패 후 Undo, 빈 patch, composite 저장/복원을 고정 사례로 만든다. 요청과 무관한 필드·영역 보존이 핵심 합격 조건이다.
- **복합 지형:** 고정 seed·맵 크기로 20개 요청을 만든다. 지원 가능 사례와 미지원 사례를 섞고, 문장 해석·엔진 실행·최종 관계 충족을 따로 채점한다. 모델 자신이 ‘잘됐다’고 판단한 것만으로 통과시키지 않는다.
- **이미지:** 정답 레이블을 만들 수 있는 지도·스케치 10개와 해석이 필요한 사진 5개를 작은 출발점으로 제안한다. 지도에는 정렬된 영역 IoU·방향·연결성을, 사진에는 관찰 가능한 특징과 대체 설명을 평가한다. 모든 사진에 가상의 정답 높이맵이 있다고 가정하지 않는다.
- **모델 비교:** 고정 입력을 반복 실행하고 모델·프롬프트·어댑터 버전을 함께 고정한다. 형식 성공률, 의미 성공률, 요청 밖 변경, 지연, 사용량을 분리한다. thinking과 토큰 예산을 동시에 바꾸면 원인 분리가 어려우므로 실험 축을 나눈다.

20개/10개/5개와 교정 예산은 시작을 위한 제안이며 검증된 최적값이 아니다. 아직 이 평가나 새로운 모델의 MapGenAI 실호출을 실행하지 않았다. 현재 모델로 과거 한계를 넘어설 수 있는지는 이 결과로 판단해야 한다.

## 8. Fable 검토와 이번 검증 범위

다른 세션에서 쓰던 Claude CLI 호출기를 재사용해 **`claude-fable-5-1` 자문을 두 차례 실행**했다. 1차는 코드 발췌를 바탕으로 독립 검토했고, 2차에는 자체 재현 결과·전체 댓글 분류·과거 사용자 결정을 제공했다. 실제 요청·응답과 모델 메타데이터를 보존했다. [1차 요청](fable-code-request.md), [1차 답변](fable-code-review.md), [2차 요청](fable-synthesis-request.md), [2차 답변](fable-synthesis-review.md)

Fable의 초기 ‘좌표 표현이 없다’, ‘이미지는 새 엔진이 필요하다’, ‘파서는 두 군데만 고치면 된다’는 의견을 그대로 채택하지 않았다. 기존 SDF/이미지 격자 코드와 파서 재현 증거로 수정했다. 자동 산을 일괄 교체하자는 제안도 기존 특징 보존 요구와 충돌하므로 대상과 연산을 구별하는 쪽으로 바꿨다. 두 모델이 동의한 것과 실제 실행으로 입증한 것은 구별한다.

2차 답변은 이 세 가지 초기 판단을 철회했다. 다만 ‘제거 목록을 매번 소비 후 비우기’, ‘색상 분할만으로 모든 top-down 이미지 처리’, ‘seed로 공급자 응답 재현 보장’ 같은 세부 제안은 그대로 채택하지 않았다. 제거 상태 유지, 이미지의 의미 구별, 모델 응답의 반복 변동을 별도로 검증해야 한다.

이번에 실제 실행한 것은 기준 소스의 격리 빌드, 기존 테스트의 빌드 확인, 원본 파서에 대한 작은 재현 검사다. **모드 빌드 성공 / 테스트 프로젝트 빌드 실패 / 파서 결함 재현**이며, 인게임 재현·새 모델의 지형 생성 품질·이미지 변환 품질은 미검증이다. 개발본·배포본·설치본 DLL 해시는 작업 전후 동일하다. [실행 로그와 재현 파일](evidence.md)
